# 旅游攻略 · 预约倒计时模块

第一个落地模块：**预约倒计时**。纯规则实现，不依赖大模型、不爬虫、不调付费 API。

解决的问题：规划行程时，你不知道自己是不是**已经错过了抢票**。马蜂窝和小红书告诉你"故宫值得去"，携程卖你"代抢服务"，但没有一个产品在你 9 月 28 日规划 10 月 1 日行程时告诉你——故宫的票 9 月 24 日就放完了，这趟去不了，换景山公园。

## 跑起来

```bash
# 国庆行程，看北京所有需预约地点的状态
python scripts/countdown.py --date 2026-10-01 --city 北京

# 指定几个地点（支持简称）
python scripts/countdown.py --date 2026-10-01 --poi 故宫 天安门 国家博物馆

# 导出手机日历：每个开票时刻提前 10 分钟响铃
python scripts/countdown.py --date 2026-10-01 --city 北京 --ics 抢票提醒.ics

# 待核实清单（人工排期照这个顺序查官方渠道）
python scripts/countdown.py --verify-list

# 重建 SQLite（改完 CSV 跑一次；countdown.py 直接读 CSV，不依赖 DB）
python scripts/load_db.py
```

### 高德接入（只在建库时用，前端零依赖）

```bash
cp .env.example .env.local          # 填入 AMAP_KEY（此文件已被 .gitignore）
python scripts/amap.py              # 自检：地理编码 / POI / 路径规划
python scripts/amap_fix_coords.py --dry          # 看坐标差异
python scripts/amap_fix_coords.py                # 校正坐标
python scripts/amap_fetch_foods.py --all --min-rating 4.3   # 批量补餐厅
python scripts/build_web.py                      # 重新编译 data.js
```

**Key 只在跑这些脚本时用一次。** 数据拉下来写进 CSV、编译进 `data.js`、
提交 git —— GitHub Pages 上是纯静态文件，别人打开链接不消耗你的额度，
也没有任何泄露风险。

坐标校正的匹配规则调了四轮，每轮都是被错配逼出来的，教训写在
`scripts/amap_fix_coords.py` 的注释里：

| 错配 | 原因 | 对策 |
|---|---|---|
| 铁路文化公园 → 倍家房产(铁路文化公园店) | 只按名称+距离 | POI 类型黑名单 + 无关词过滤 |
| 第八市场(八市) 被误拒 | 按大类拉黑太粗（菜市场归"购物服务"） | 名字对上就不看类型 |
| 水陆庵 → 水陆庵中学 | 名字包含判定在过滤之前 | 把"挂在景点名下的其它场所"检查提到最前 |
| 湖南博物院 → 湖南省地质博物馆 | 中文常用字天然重合 80% | 要求查询名的**每个字**都命中 |
| 回车巷 → 成安县的回车巷 | `city_limit` 只限到市级 | 移动 > 10km 的人工确认 |

### 导出单条线路为 HTML

```bash
node scripts/export_guide.js 北京 厦门 4
# -> exports/北京-厦门-攻略.html
```

单页自包含（内联 CSS），可直接双击打开、发给别人、或打印。内容：花费总览、
逐日行程、交通对比、到站接驳、住宿片区、美食（含**数据来源对照表**）、
景点清单、出发前必办、数据边界。

**行程生成直接复用 `index.html` 里的 `buildPlan`** —— 不另写一套，
否则网页端和导出版会算出不一样的行程。

行程里会自动标出三件事：
- 需预约的景点带 `🎫 需提前预约` 和渠道、提前天数、抢票难度
- 单次转场超过 35 分钟标「较远」，提示可以挪到顺路的那天
- 景点排完后剩余时间给「自由安排」占位，不留空白

```bash
python -m http.server 8777
# 打开 http://127.0.0.1:8777/preview.html
```

`preview.html` 是评审用的页面：左边手机框里用 iframe 跑<b>真实的</b> `index.html`，

场景靠 URL 参数驱动，这几个参数生产环境也能用来调试：

| 参数 | 作用 |
|---|---|
| `?now=2026-09-24T19:00` | 模拟"当前时刻"，用来演示开票当天 / 已错过 |
| `?demo=1` | 用演示规则集（存在独立 localStorage key，**绝不碰真实数据**） |
| `?date=2026-10-01&city=北京` | 指定初始游览日与城市 |
| `?view=kb&kbfrom=邯郸&kbto=北京&kbtab=攻略&kbdays=4` | 直接打开某条线路的指定 tab 与天数 |

### 四个页签

- **倒计时** —— 选日期 + 选城市，按紧急度分组显示；底部可导出开票提醒到手机日历
- **攻略** —— 先选出发地和目的地：
  - 没选目的地 → 列出从这里能去的所有地方（按车上时间排，标出本月不该去的）
  - 选了外地 → 五个 tab：**攻略 / 路线 / 景点 / 美食 / 住宿**
  - 选了本市 → 本地游，不算往返交通，改成**市内交通** tab
  - 「攻略」tab 把整条行程按天排出来（DAY 1/2/3…、每项带时段、含往返交通与饭点），
    并给出人均花费估算；在「景点」「美食」页**勾选想去的**，攻略会只按你选的重排
- **规则库** —— 42 条规则可搜可筛，点开就能改（改动只存本机 localStorage，不动仓库）
- **待核实** —— 按优先级排的清单，前 8 条标红。在手机上查完官方渠道直接填，
  再用「导出修正 CSV」把结果拷回电脑，覆盖 `data/booking_rules.csv` 后重跑
  `build_web.py` 即成为新基线

### 两套实现一致性

`scripts/countdown.py`（命令行）和 `index.html`（网页）各有一份状态机。
两者已用 339 个「规则 × 日期」组合交叉验证，9 个状态分支全部覆盖、输出完全一致。
**改动任何一边的判定逻辑，必须同步改另一边。**

### 数据里的几个"不看会踩坑"样本

这类结论是知识库的主要价值，光有景点名单没用：

| 目的地 | 结论 |
|---|---|
| 鼓浪屿 | 瓶颈是**船票**不是门票，节假日船票比岛上任何门票都难买 |
| 厦门 | **厦门站在市区，厦门北站在集美进岛要 50 分钟** —— 买票最容易踩的坑 |
| 鼓浪屿住宿 | 住岛上能看到没游客的清早，但行李要自己拖着走石板路 |
| 八市海鲜 | 加工费和单价必须先谈、要看秤，这是最容易被坑的环节 |
| 全聚德 | 人均高且评价两极，本地人更多去四季民福 |
| 独库公路 | 只有 7-9 月能走，其余九个月整条路不通 |
| 邯郸 → 上海 | 高铁要换乘 ¥560，夜车硬卧直达 ¥250 还省一晚酒店 |
| 邯郸本地 | **全市没有地铁**，主要景点（广府古城、娲皇宫、响堂山）都在郊县，10 条接驳里 6 条只能打车 |
| 邯郸车站 | 普速车到的**邯郸站在市区**，反而比高铁的邯郸东站更靠市中心 |
| 张家界 | **内部交通才是瓶颈**：百龙天梯与索道排队常超 1 小时，住景区门口才能赶第一班 |
| 长沙文和友 | 排队常 3-4 小时，本地人基本不去了；想吃虾去社区虾店 |
| 凤凰古城 | 白天观感普通，**只安排白天等于没看到凤凰** |

### 三线城市的交通结构差异

邯郸作为京广线上的三线城市，21 条路线里 **14 条需要换乘**，远程目的地必须先到郑州或
北京转机。同样问"3 天能去哪"，从邯郸和从上海出发的答案完全不同 ——
推荐引擎不能统一用小时数当半径，要把"到枢纽的时间"算进往返成本。

| 邯郸出发 | 门到门 |
|---|---|
| 安阳殷墟 | 97 min |
| 石家庄 / 郑州 | 140-150 min |
| 北京 | 235 min |
| 上海（需郑州或徐州换乘） | 480 min |

### 什么进库，什么实时查

这是最关键的设计判断：

| 数据 | 变化频率 | 处理 |
|---|---|---|
| 目的地标签、最佳月份、海拔 | 年 | 存库 |
| 景点坐标、停留时长、门票 | 年 | 存库 |
| 网红/小众标记、出片指数 | 半年 | 存库 |
| 餐厅店名、人均 | 半年 | 存库，**必须带榜单来源和核实日期** |
| 城际交通方式、耗时、票价区间 | 较稳 | 存库 |
| **具体车次号 / 航班号** | 天 | **不存** —— 一次调图就全废，给 12306 入口 |
| **市内换乘方案、公交实时到站** | 实时 | **不存** —— 高德给得更准 |
| 酒店实时价 | 天 | 只存档位基准 |

### 人工整理 vs 自动拉取

这是全库最要紧的一条区分，UI 和导出里都标了出来：

| | 人工整理 | 高德自动拉取 |
|---|---|---|
| 景点 | **135 条**（网红 39 / 小众 51 / 经典 45） | 1185 条（标「未分类」） |
| 有出片指数、最佳光线、机位 | ✅ | ❌ |
| 有避坑提示 | ✅ | ❌ |
| 有真实评分和营业时间 | ❌ | ✅ |
| 美食 | **112 条**（老字号 + 地标老店，带避坑） | 1299 条（有评分人均） |
| 住宿 | **34 个片区**（写清地铁覆盖和坑） | 138 个（按景点密度自动圈） |
| 路线 | **125 条**（实录车次票价换乘） | 1397 条（按直线距离估） |

**排行程时一律优先用人工那批** —— 自动拉的只在人工的用完后补位。
因为「文和友排队 3-4 小时本地人不去」「厦门北站不在市区」这类信息，
接口永远不会告诉你。

自动拉取的三个脚本：

```bash
python scripts/amap_fix_coords.py            # 校正景点坐标
python scripts/amap_fetch_pois.py --gaps     # 补还没景点的目的地
python scripts/amap_fetch_foods.py --gaps    # 补还没美食的城市
python scripts/amap_fetch_stays.py --gaps    # 按景点密度圈住宿片区
python scripts/gen_routes.py                 # 生成估算路线（无接口可用）
python scripts/build_web.py                  # 重新编译 data.js
```

`gen_routes.py` 是纯计算不调接口 —— **高德和 12306 都没有公开的城际班次接口**，
高铁车次、票价、班次密度拿不到，只能按坐标距离推（实际里程≈直线×1.3，
高铁等效 200km/h、0.45 元/公里；1200 公里以上按飞机算）。
误差不小，所以这批在界面上带「估算」角标。

### 旅行强度

首次进入会问一次，之后可以在攻略页顶部随时切：

| | 出门 | 一天几个点 | 每处时长 | 能忍多远的转场 |
|---|---|---|---|---|
| **懒人** | 10:00 | 最多 3 个 | ×1.35 | 30 分钟，不爬山 |
| **正常人** | 09:00 | 最多 5 个 | ×1.0 | 55 分钟 |
| **狠人** | 07:30 | 最多 8 个 | ×0.68 | 95 分钟 |

同样是北京→厦门 4 天：懒人排 7 个点、平均每处 149 分钟；
狠人排 16 个点、平均 57 分钟，而且只用 3 天就走完了。

### 交通时间只展示「车上时间」

`routes` 表里还存着 `access_min` / `egress_min` / `buffer_min` / `total_min`，
但**前端一律不读不显示**。

原因：那几段是「市中心 ↔ 车站」的估值，而库不可能知道用户住在城市哪个位置。
在浦东还是虹桥，到虹桥站差 40 分钟。把估值当数据展示出来只会误导，
所以只显示 `duration_min`（车上时间），并在页面上注明"出门请自己往前留"。

字段保留是为了以后接高德路径规划做实时计算 —— 那属于在线算，不属于库。

### 数据边界（必须知道）

- **店名是真的**（中华老字号 40 条、地标老店 30 条），但**人均全部是估值**，
  `price_confidence` 一律标 `low`，出门前请再确认
- **坐标 129/135 已用高德校正**（真值），剩 8 条是估值且在 `note` 里标了
  「坐标未校正」。我原来对郊县景点估得很差 —— 龙泉山偏 24km、邺城博物馆偏
  18.8km、京娘湖偏 16.5km
- **4766 条全部 `verified=0`**，没有一条对过官方渠道。`v_kb_stale` 视图列出全部待核实项
- **住宿只到片区级**，给三档房价区间 + 旺季系数，不给单店实时房价（携程系需企业资质）
- **美食 367 条分两类**：112 条人工录入（老字号与地标老店，**带避坑提示**，
  人均是估值）+ 255 条高德拉取（**有真实评分、人均、营业时间，但没有避坑**）。
  评分来自高德自己的数据，**不是大众点评** —— 点评没有开放接口、抓不到。
  排行程时优先用人工那批，高德那批留给浏览
- 8 城有景点美食，其余 64 个目的地**只有骨架**（有季节窗口和偏好分，无景点美食明细）
- 新疆、川西的景点与美食**尚未填充**（只有目的地骨架与季节窗口）
- 还有 11 个城市有路线但没进目的地库（武汉、济南、郑州、石家庄、太原、黄山等）
- `hot_type`（网红/小众）和七个偏好分是**主观评估**，不是统计数据

## 状态机（核心逻辑）

```
need_booking = 0                      -> NO_BOOKING     无需预约
advance_days < 0                      -> UNKNOWN        规则未核实，算不出倒计时
release_mode = onsite                 -> ONSITE         现场取号

开票日 = 游览日 − advance_days

release_mode = rolling（窗口内随时可约）
  今天 < 开票日                       -> WAITING        还有 N 天开窗
  今天 ≥ 开票日                       -> BOOKABLE_NOW   现在就能约

release_mode = fixed_time（定点放票，唯一"错过就真没有"的模式）
  今天 < 开票日                       -> WAITING        倒计时 + 难度≥4 提示设闹钟
  今天 = 开票日，当前时刻 < 放票时刻   -> ACTION_TODAY   今天 X 点开抢，还剩 N 小时
  今天 = 开票日，当前时刻 ≥ 放票时刻   -> RELEASED_TODAY 今天已放票，去查余量
  今天 > 开票日                       -> MISSED         按难度分级判断还有没有戏
```

`MISSED` 必须分级，否则会误伤那些其实还有余票的场馆：

| 难度 | 结论 |
|---|---|
| ≤ 2 | 该馆通常不紧张，大概率仍有余票，直接去查 |
| 3 | 可能还有余票，尽快查；留意退票 |
| ≥ 4 | 基本无票，直接走备用方案（输出会带上 `backup_poi` / `backup_plan`） |

难度口径：`1` 不用抢 / `2` 提前 1–2 天够 / `3` 开票当天 / `4` 开票即抢 / `5` 秒杀级。

## 数据治理（这张表是人工维护的，必须留痕）

初始 42 条里 **只有 2 条 `advance_days` 有依据**（故宫、国博均为提前 7 天），其余全部 `advance_days = -1`，状态会显示 `UNKNOWN` 而不是编一个数字出来。这是故意的——预约规则编错比不给更糟。

三个字段控制可信度：

- `src_confidence` = `high` / `mid` / `low`：初始录入的依据强度
- `verified` = 0：未对过官方渠道；每条输出都会带 `[待核实]` 角标
- `last_check_date`：超过 90 天进 `v_stale_rule` 视图，前端标"规则可能已变"

核实流程：`--verify-list` 按「难度降序 + 信息缺口降序」排出顺序 → 逐个查官方渠道 → 回填 `advance_days` / `release_time` / `source_url` / `last_check_date`，把 `verified` 改 1。**先查前 8 条**（难度 5 星且提前天数未知的那批），它们决定了这个功能有没有用。

`v_verify_priority` 视图给出同样的排序，供 SQL 侧使用。

## 现有产品怎么做的（调研结论）

| 产品 | 做法 | 对我们的启示 |
|---|---|---|
| **Google Maps** Popular Times | 聚合 opt-in Timeline 用户的手机位置密度，用「**占该地点自身峰值的百分比**」表示，100 = 史上最挤；能检测实时突增标 Live；差分隐私保护 | 用相对百分比而非绝对人数，**绕开了"必须知道承载量"的难题**，值得抄 |
| **百度地图** 景区热力图 | 基于基站/位置聚类算人群密度与流速，10 分钟更新，但只覆盖 13 城 118 个商圈景区；**开放 SDK 只负责渲染，数据要开发者自己传** | 印证了实时人流拿不到，只能自己预测 |
| **Wanderlog** Optimize Route | 选起终点或 auto-suggest → 单日重排 → **优化后显示 what's changed，可一键 revert**；Pro 功能 $39.99/年 | 「重排后给 diff + 允许撤销」是行业验证过的做法，直接照做 |
| **携程 / 美团 / 飞猪** | 是故宫等景区的官方授权平台，卖的是**代抢服务（收服务费）**；抢票功能集中在火车票 | 它们在你**已经决定去**之后卖代抢，没有人管你在**规划阶段**是否已经错过。我们的位置就在这个空档里 |
| **文旅部 / 地方文旅** | 国标《景区最大承载量核定导则》LB/T 034—2014 强制公开承载量；达 80% 启动限流、达 100% 停止售票；微信「一码通」在 A 级景区推广 | 承载量是公开的（拥挤度的分母）；**预约余量趋零就等于接近承载量**，是最好的实时代理信号 |

结论：**我们不做抢票工具，做规划期的时间轴对齐。** 定位不与携程冲突，也不需要它们的接口。
